## A01 — P1 — Guided market-sizing notes bypass private-data controls

**User reproduction:** Install the shipped `public/question-pack-market-sizing-cookbook.mathdrill.json`. Open Market Sizing for that pack and choose its first exercise, Reusable Container Pickup Demand. Enter `500000`, `10%`, `8`, and `$6` for its numeric assumptions, and private text in **Optional note on the adoption assumption**. Complete the exercise with `$2.4M`. Optionally add a separate self-review note on the last stage. In Settings, download Standard Progress Export and Complete Backup with the private-text scope unchecked. Both files contain the assumption note. Clear Personal Data: the self-review note disappears, but the assumption note remains in IndexedDB. If there is only an assumption note, Settings counts zero saved notes/personal items and disables personal clearing.

**Expected/actual:** Settings says Standard exports exclude notes (`src/features/settings/LocalSettingsView.tsx:734`), the optional scope says it includes notes (`:765`), and Clear Personal Data says it removes market-sizing note text (`:1006`). The shipped pack explicitly labels the field a note (`public/question-pack-market-sizing-cookbook.mathdrill.json:77-81`). These controls apply only to the top-level self-review `note`, leaving guided `inputKind: "note"` values exposed. This is a local privacy-control failure; these probes found no transmission of the note to a service.

**Root cause/current lines:** `src/features/market-sizing/marketSizingPersistence.ts:43` indiscriminately copies all guided values into `inputValues`. Standard redaction at `src/features/settings/localProgressExport.ts:73`, Complete redaction at `src/features/settings/completeBackup.ts:251` and `completeBackupSet.ts:89-91`, private preservation at `privateDataPreservation.ts:20-24`, and personal counting/clearing at `personalDataClear.ts:44-47,62-64` only recognize the top-level `note`. The saved attempt contains no durable metadata distinguishing note inputs from numeric/choice inputs after a pack changes or is removed.

**Suggested fix:** Store guided note values separately, or persist their field identities, and use the same privacy classification for Standard export, Complete scope filtering, inventory, personal clearing, and preservation during an unselected-private-scope restore. Account for existing installed-pack attempts and missing/replaced packs in the migration. Numeric assumptions, scores, and attempt identity can remain ordinary progress.

**Acceptance:** The shipped cookbook's guided note is absent from Standard and Complete without private text, present in Complete with private text, counted in Personal Data, removed by personal clearing, and preserved when restoring progress without selecting private text. Cover replacing/uninstalling the source pack. Numeric assumptions and scores remain unchanged.

**Evidence:** `guided-note-browser.mjs` / `guided-note-browser.json` assert actual downloads and native IndexedDB after actual UI clearing; `guided-note-private-clear.png` shows the zero-note inventory afterward. `guided-note-boundaries.mjs` / `.json` independently exercise production persistence, both backup paths, count, and clear. Browser assertions passed with no page errors. This was not reported in the Sept22 audit; that audit's S4 concerned empty top-level note counting, which is fixed.

## A02 — P1 — Stale full-case drafts overwrite newer saved work

**User reproduction:** In tab A open `/case-practice/simulation/` and opt into **Save a private draft on this device so I can resume this case.** Open the same route in tab B, leaving its **Resume draft** prompt waiting. In A type a new question and wait until it is saved. Click Resume draft in B. Without editing a question in B, its autosave replaces A's saved question with the older blank text, while both tabs show the draft as saved. Uncheck draft saving in B; the draft is deleted. Edit A again; A silently recreates that deleted private draft.

**Root cause/current lines:** The draft key is shared by simulation ID (`src/features/case-practice/simulation/fullCaseDraft.ts:6-7`). `FullCaseSimulation.tsx:131-136` reads a draft once. `resumeDraft` uses that captured `pendingDraft` at `:237-248`; enabling autosave triggers `:212-221`. Writes/deletes are unconditional at `:157,160`; `pendingDraftWrites` at `:65` only serializes operations within one document. The lifecycle-generation mechanism for destructive whole-data changes does not detect another tab's same-record edit or opt-out deletion. Revision checks currently exist for drill sessions, not this practice-record draft (`src/lib/storage/indexedDbAppStorage.ts:94,336-340`).

**Suggested fix:** Give private drafts a per-record revision/ownership token and atomically compare it before saving or deleting. Resume should reread the latest draft or reject a changed revision; stale saves/deletes must produce a conflict notice preserving the user's in-memory text. Prevent delete/recreate ABA, and notify other tabs when a draft is explicitly deleted.

**Acceptance:** Two tabs reading one revision cannot overwrite one another's later draft; resuming the old prompt never replaces newer saved content. A stale delete cannot erase a newer draft, and an opt-out deletion cannot be silently recreated by a stale writer. Conflict feedback retains local work; same-tab ordered autosaves, retry, Reset, and completed-draft recovery still work.

**Evidence:** `multi-tab-private-draft.mjs` / `.json` contain initial/A-saved/B-resumed/deleted/recreated native IndexedDB snapshots. `draft-tab-a-stale-saved.png` and `draft-tab-b-resumed.png` show the two views. Browser exited 0, no page errors. Sept22 S1 was stale drill-session overwrite; current drill CAS fixes do not cover full-case draft writes.

## A03 — P2 — Early drill input causes a false storage conflict

**Location:** `src/features/drills/ActiveDrillSession.tsx:382–386`, `:557`, `:817`; token assertion in `src/features/drills/drillPersistence.ts:117–120`.

**Impact:** A single-tab learner with an existing unfinished attempt can answer the initial freshly generated question before its draft finishes loading. The app then refuses to persist those new answers and presents an incorrect “changed in another tab” warning.

**Cause:** Answer input and submission are enabled while `draftLoaded` is false. Draft recovery adopts the old draft's existing-record token at line 382, but skips restoring its session when the freshly generated session already has a response at line 386. The next write applies that old token to the new session ID, whose record does not exist, and correctly fails the token check. The mismatch originates in the UI's recovery lifecycle, not concurrent storage activity.

**Controlled real-component reproduction:**

1. Save an unfinished two-question Addition drill with one correct response.
2. Render `ActiveDrillSession` with a newly generated session having the same route/settings draft key. Delay the storage page read used for recovery.
3. The Answer field is enabled. Enter the fresh question's correct answer and Submit; “Correct” feedback appears.
4. Release the read. The app reports “This attempt changed in another tab. Your answers are still here. Choose which attempt to keep working with.”
5. The old record still has one response; the fresh session record is absent. No other tab exists in the probe.

**Evidence:** Passing `workflow-probes.test.tsx` test “early answer during draft loading skips the saved attempt and incorrectly reports a cross-tab conflict”. It renders the production component and uses the existing `MemoryAppStorage` implementation, delaying only the read boundary.

**Suggested fix:** Resolve recovery before allowing answer, skip and submission actions, or explicitly keep the token paired with the session actually selected when recovery is bypassed. Gate recovery-dependent controls consistently, including expiration behavior.

**Acceptance test:** Defer draft loading with an existing attempt, attempt early interaction, then release loading. Under the chosen recovery policy, the resumed or intentionally retained fresh session uses its own matching token, produces no false conflict, and persists the next submitted answer correctly. Recovery-dependent timers must follow the same policy.

## A04 — P2 — Language changes discard benchmark state

**Location:** `src/features/question-packs/SpecializedQuestionPackContent.tsx:227` and `:255`; supporting lines `:196`, `:299–306`, and `src/features/benchmarks/benchmarkSession.ts:26–27`.

**Impact:** The Language control discards the answer currently being typed. After completion, the same control replaces Session Results with a fresh timed benchmark without an explicit start action. The completed result remains stored; this finding concerns the lost active answer and changed current view/run.

**Cause:** `QuestionPackBenchmarkSession` consumes the locale context and calls `createBenchmarkSessionResult` during every render. The helper creates a new timestamp and session ID. That ID is the React key of `ActiveDrillSession`, so a language rerender remounts it. For an unfinished benchmark, persisted responses can reload, but the unsubmitted input cannot. A completed benchmark is not an unfinished draft and therefore becomes a new run.

**Production browser reproduction:**

1. Open `/benchmark/` and begin the default Beginner Benchmark.
2. Type `987654321` into Answer, then change Language from English to French.
3. The answer changes from `987654321` to an empty string. IndexedDB session count remains one in this unfinished-run probe.
4. In a fresh benchmark navigation, skip all 20 questions and wait for “Session saved on this device.”
5. Change Language from English to French. Before the change, Session Results is present and there are zero numeric-answer inputs. Afterwards, the results heading is absent and a numeric-answer input appears. The screenshot shows Question 1 of 20, zero answered, and a new 20:00 timer.

**Evidence:** `browser-locale-results.json`, cases “benchmark language change loses draft answer” and “benchmark completed summary language change starts a new run”; screenshots `benchmark-locale-switch.png` and `benchmark-summary-locale-switch.png`.

**Suggested fix:** Create the benchmark session once for a stable benchmark/route/timing identity. A locale update should change labels while retaining the mounted active session and summary. A scoped child with initialized state avoids memoization against newly allocated merged benchmark objects.

**Acceptance tests:** Switch language while an unsubmitted benchmark answer is present and after saving the completed summary. The input, session identity, responses, completion state and summary remain intact; the latter transition starts no new timer or session record.

## A05 — P2 — Language changes switch an active Fit rehearsal

**Location:** `src/features/case-practice/fit/FitPracticeView.tsx:108–109` and `:125`; caller `src/features/question-packs/CasePracticeQuestionPackContent.tsx:109`, `:320`; consequence `FitPracticeView.tsx:377`.

**Impact:** An active rehearsal silently switches to a different story and competency even though the rehearsal controls are locked while running. Its self-review is then recorded under a prompt the learner did not start rehearsing.

**Cause:** The wrapper rebuilds all prompt arrays when locale context rerenders. Fit's load effect depends on the prompts array. On every reload, it unconditionally selects the first stored story and the first prompt for that story's competency. The running phase is retained, so this bypasses the normal selection/reset flow. `saveReview` reads the newly selected prompt ID instead of a captured rehearsal identity.

**Production browser reproduction:**

1. Have two saved stories: a newer Leadership story and an older Conflict story. The probe seeded valid synthetic records with IDs `synthetic-story-0` and `synthetic-story-1`.
2. Select the older Conflict story and start the `conflict-stakeholder` rehearsal.
3. Change Language from English to French during the rehearsal.
4. The story changes from `synthetic-story-1` to `synthetic-story-0`; the prompt changes from `conflict-stakeholder` to `leadership-uncertainty`. The timer remains 2:00 in this immediate transition and “Terminer la répétition” confirms the rehearsal remains active.
5. Finish and save the self-review. The persisted attempt has `itemId: leadership-uncertainty`, although the started prompt was `conflict-stakeholder`.

**Evidence:** `browser-locale-results.json`, case “fit language change during rehearsal”; `fit-locale-switch.png`, visually inspected.

**Suggested fix:** Stabilize equivalent prompt arrays and initialize story selection only when there is no valid existing selection. Retain the active rehearsal's story/prompt identity through asynchronous loads and capture that identity when the rehearsal starts, so its saved review cannot drift.

**Acceptance test:** With two competencies, start the nonfirst story, switch language while running, finish and save. Selected story/prompt and elapsed rehearsal state stay stable; the saved review references the originally started prompt.

## A06 — P2 — Accepted large records block every backup path

**User reproduction:** Import a valid sizing template with the permitted maximum 30 input steps: one required numeric input and 29 optional note inputs. Paste 100,000 U+0001 control characters into each note, enter `1`, complete and save the attempt. This is an intentionally extreme supported-input boundary, not a typical note. In Settings, Standard export fails and tells the user to use Complete Backup. Complete also fails: **Complete backup progress: Import file must be 10485760 bytes or smaller.** Omitting private text does not help because those note inputs are in mandatory progress. Individual-record recovery reports no incompatible records, so it offers no remedy for this record.

**Observed size:** Native Chromium IndexedDB saved one record whose compact JSON is **17,401,563 bytes**. Each note satisfies the 100,000-character stored-string cap; JSON's `\u0001` escaping expands each character to six bytes. The production-function probe produces 17,401,474 bytes with fixed timestamps/IDs.

**Root cause/current lines:** Accepted pack steps allow 1–30 inputs (`src/features/question-packs/questionPackMarketSizing.ts:127-128`). The note textarea is unbounded (`MarketSizingGuidedForm.tsx:957-965`); persistence copies all values at `marketSizingPersistence.ts:43` and saves at `:58`. `src/lib/validation/inputLimits.ts:15-46` bounds strings, collections, and depth but has no total persisted-record JSON-byte cap. Complete's multipart builder keeps records intact and only flushes a non-empty chunk (`completeBackupSet.ts:99-104`), so a large single record stays in one part. That part then calls `createCompleteBackup` at `:118`, whose progress validator (`completeBackup.ts:391`) inherits Standard's 10 MiB limit (`localProgressExport.ts:17,654-655`), despite the advertised 40 MiB Complete-file and 128 MiB set bounds. Record diagnostics checks shape/resources but does not flag aggregate serialized record bytes (`recordDiagnostics.ts:12-44`).

**Suggested fix:** Define one coherent record/file byte contract. Complete progress validation can use its own file bound rather than Standard's inner 10 MiB bound, while partitioning and write validation guarantee each record fits a restorable part. If rejecting oversized records instead, validate the total serialized bytes before committing and retain editable input with a clear error. Handle already-saved oversized records without requiring a whole-history reset. Fixing A01 will exclude guided notes from non-private backups but does not resolve Complete with private text selected.

**Acceptance:** The same valid 30-step input is either rejected before storage with retained user text, or exports and restores through Complete with correct contents. Standard may still recommend Complete for aggregate history limits. A single record near the part boundary, including worst-case JSON escaping and envelope overhead, never produces an unexportable saved record. Existing large records have an explicit recovery/export path.

**Evidence:** `guided-note-browser.mjs` / `.json` verify actual import, UI save, native persisted byte size, and both UI export errors; `guided-note-capacity.png`. `guided-note-boundaries.mjs` / `.json` verify production partition validation and empty recovery diagnostics. No browser page errors. Sept22 S2's single string over 100,000 characters is now blocked by write guards; this is a different aggregate-byte gap using only accepted string lengths.

## A07 — P2 — A stale initial load hides newly saved Fit stories

**Location:** `src/features/case-practice/fit/FitPracticeView.tsx:103–104` and `:178–189`.

**Impact:** Saving a valid story during initial story-bank loading can succeed in IndexedDB and appear briefly, then disappear from the bank when the earlier load finishes. The bank claims “0 saved” despite the saved record. The learner has no visible way to select that story until reloading and may save it again.

**Cause:** The form allows submission during the loading status; its guard checks only “saving”. A successful save merges the new record into local state at line 189. The outstanding initial load later replaces that state with its older snapshot at line 103 and resets the status without checking for intervening edits. This is independent of language changes and requires only one tab.

**Controlled real-component reproduction:**

1. Render Fit with the first story-bank read delayed and an empty snapshot captured for that read.
2. While “Loading stories saved in this browser...” is visible, fill Story title, Situation, Task, Action, Result and Reflection with valid synthetic text and Save Story.
3. Verify the new story heading appears and a `fit_story` record exists in storage.
4. Release the earlier empty load. The story heading disappears and the bank shows “0 saved”; the saved `fit_story` record remains in storage.

**Evidence:** Passing `workflow-probes.test.tsx` test “saving a Fit story before initial load resolves leaves it saved but absent from the story bank”.

**Suggested fix:** Guard initial load results against intervening story mutations, merge the snapshot with completed local changes, or prevent story mutations until initial recovery finishes. Keep load status separate from mutation status so a stale loader cannot overwrite the save state.

**Acceptance test:** Delay an empty initial read, save a valid story, then resolve the stale read. If early saving is supported, the new story remains visible and selectable and its count agrees with storage. If saving is gated, the form becomes usable once recovery has completed.

## A09 — P2 — Accepted numeric tolerances produce false arithmetic errors

- Primary location: `src/lib/validation/validateAnswer.ts:174-189`, particularly line 187.
- Impact: legitimate partial-credit answers receive zero instead of 50 points, and progress/recommendation error history records arithmetic errors where the accepted calculation is correct.
- Reproduction: import the valid public fixed-numeric starter with answer `{value:100,unit:"users",tolerance:{type:"absolute",value:5}}`; submit through production `submitAnswer`, selected unit `users`, 30 seconds. `100 years` returns numericMatch true, unit_error only, score 50. `102 years` returns numericMatch true and feedback "The number is correct, but the unit does not match", but errors `[unit_error, arithmetic_error]` and score 0. `102 users` is correct.
- Actual callers: `answerSubmission.ts` uses this shared validator; `scoringEngine.ts:72-91` makes arithmetic_error zero out unit-only partial credit. The validator is also used by Interview Math, market sizing, exhibits, and full cases.
- Root cause: numeric classification uses absolute exact epsilon instead of the already-computed numericMatch for the final arithmetic branch. Magnitude and percentage-point classifications likewise are not consistently gated by numericMatch.
- Suggested fix: classify numeric error types only when the normalized numeric candidate is not accepted. Preserve unit_error alone when numericMatch is true.
- Acceptance check: exact and tolerance-accepted answers with the same wrong unit have the same unit-only classification and partial score; outside-tolerance answers still include the relevant numeric error. Cover absolute, relative, and range tolerances, percentage answers, accepted alternate percentage notation, and overlapping numeric error checks.
- Probe: `probes.test.ts`, "confirms a numerically accepted answer ...".

### Implementation contracts

The detailed expected behavior and acceptance criteria above define the functional specification. Implementation should preserve the existing static export, deterministic bundled generation/grading/recommendations, IndexedDB progress, installable PWA, and same-origin offline practice.

The storage work needs three consistent contracts: a durable classification of every private note field, atomic per-record revisions for shared drafts including deletion, and serialized record/file bounds that agree across writing, diagnostics, export and restore. Schema changes must include explicit compatibility/migration handling for existing saved attempts and supported historical backups. Preserve saved work on rejected writes and conflicts; replacement and clearing must keep their transactional rollback and generation guards.

The workflow work needs a stable exercise/session identity across display-only changes, paired recovery state and storage tokens, and asynchronous reads that cannot overwrite later local edits. The grading work should continue using pure deterministic validators and scorers. Accepted numbers must have consistent classifications and partial credit; authoring schemas/readers must preserve supported currency metadata; variable validation, generation, formatting and capacity must agree on the supported precision.

The performance work should reuse native IndexedDB counts, existing workers and current cancellation/request identities. Keep heavy data inside a worker where practical and return compact results, rather than introducing a new framework or moving a large clone back to the UI. Retain bundled worker caching, CSP compatibility and the verified offline bootstrap behavior.
